GPU 入门：从一次 ReLU 到 FlashAttention

训练和运行大模型几乎全在 GPU 上。学过计组，你知道 CPU 怎样取指、执行、访存，知道 Cache、DRAM、流水线；可一打开显卡的资料，迎面就是 SM、warp、HBM、Tensor Core、FlashAttention 一串名词。这篇从一个具体的问题出发，把这些东西一样一样摆到一块真实的显卡上。

先看一组让人意外的数。一块 NVIDIA H100 显卡，号称每秒能做约 989 万亿次运算（这个数指的是矩阵乘法，第 2.5 节会说明为什么要加这个限定）。可是让它对一个 64 MB 的数组做最简单的操作——把每个负数换成 0——实际只跑出每秒 0.44 万亿次，不到号称的两千分之一。换成两个 4096×4096 的矩阵相乘，它又能跑到接近号称的速度。同一块显卡，为什么有的活快得惊人，有的活慢得出奇？这篇就是要回答这个问题。回答的过程中，GPU 的各个部件会依次出场；最后用学到的东西读懂 FlashAttention，一个让大模型里“注意力”计算快了好几倍的方法。

内容展开的是 Stanford CS336《Language Modeling from Scratch》（2026 春季）第 5 讲《GPUs》（Tatsu Hashimoto 主讲），并吸收了第 6 讲开头对 GPU 硬件和编程模型的回顾。课程的顺序是：GPU 怎么工作 → 什么决定快慢 → 用这些知识读懂 FlashAttention，本文也按这个顺序。计组里讲过的东西（Cache、DRAM 的突发传输、流水线、寄存器）直接拿来用；计组以外的东西，第一次出现时都会先交代。

几个先说清楚的词。

  • 浮点运算次数（FLOP）：一次浮点加法或乘法算一次。TFLOP/s 是每秒一万亿次浮点运算，衡量算得多快。989 TFLOP/s 就是每秒 989 万亿次。
  • 张量：深度学习里对多维数组的叫法。一个 4096×4096 的矩阵就是一个二维张量。
  • PyTorch：最常用的深度学习库，用 Python 写。torch.relu(x) 是它的一个函数；x 放在显卡上时，计算由显卡完成。
  • ReLU：神经网络里最常见的一步运算，把每个负数换成 0、正数不变：\(\mathrm{relu}(v) = \max(v, 0)\)。
  • float32、bf16：float32 是计组里讲过的 32 位单精度浮点数，每个占 4 字节；bf16 是一种 16 位浮点格式，每个占 2 字节，深度学习里常用（第 6.2 节细讲）。

全文用同一台机器、同一个例子：

  • 机器：一块 NVIDIA H100 SXM 显卡，时钟约 1.98 GHz，1 个周期约 0.5 ns。
  • 数据：一个 4096×4096 的 float32 矩阵 x，共 16 777 216 个数、64 MB，已经放在显卡自己的内存（显存）里。
  • 第一件事：y = torch.relu(x)。后面还会用到矩阵乘法 x @ W（神经网络里每一层的主要计算）和注意力里的 softmax。

1. 为什么要有 GPU：同样多的晶体管，花在哪

1.1 CPU 变快的老路走到了头

从 1980 年代到 2000 年代前期，晶体管越做越小，同样的功耗下主频越来越高（这叫 Dennard 缩放），同一个程序不用改就自动变快。大约 2005 年以后这条路走到头：晶体管还在变多，主频却停在 4–5 GHz 附近，再往上，功耗和发热就压不住了。多出来的晶体管不能再用来“把一件事做得更快”，只能用来“同时做更多件事”。

GPU 就是把这条路走到底的芯片。CS336 引用 NVIDIA 首席科学家 Bill Dally 的数据：单芯片的推理性能（推理指用训练好的模型算结果），从 2012 年的 K20X 约 4 TOPS 到 2023 年的 H100 约 4000 TOPS（TOPS 是每秒万亿次运算，这里以 8 位整数运算计），十年涨了约一千倍。他把这一千倍拆开算过：数值格式从 32 位降到 16 位再到 8 位，贡献约 16 倍；“复杂指令”——一条指令完成一个点积或一小块矩阵乘加——约 12.5 倍；制程从 28 nm 到 5 nm 约 2.5 倍；稀疏化（权重里大量为 0 的部分跳过不算）约 2 倍；模型本身的效率也在提高。制程只占很小一份，大头是“用更少的位数”和“一条指令干更多活”，也就是后面要讲的低精度（第 6.2 节）和 Tensor Core（第 2 节）。

为什么大家要不停地堆算力？CS336 开头放了 Kaplan 等人的扩展律曲线：语言模型的验证损失（衡量模型在没见过的文字上猜得有多不准，越低越好）随训练算力 \(C\) 按 \(L \approx 2.57\,C^{-0.048}\) 平稳下降，算力多一个数量级，损失就可预期地降一截。

1.2 CPU 的核心和 GPU 的 SM 长得不一样

🖼 请对照左栏 ①：CPU 核心与 SM：晶体管花在哪（可交互）⧉ 单独打开

同样是一大块晶体管，CPU 和 GPU 花的地方很不一样。拿 ReLU 来比：盯住 x 开头的四个数 −3、2、−1、5，要把它们变成 0、2、0、5。

先看 CPU 的一个核心（左栏 ① 第一步）。现代 CPU 也能一次算好几个数：它有向量寄存器，一个能装 16 个 float32；还有向量运算单元，一条指令把 16 个数同时算完。四个数从内存经三级缓存进入向量寄存器 v1，一条 max 指令就得到 0、2、0、5。可是在核心里，向量运算单元只占一小块。占地方的是另外三样东西：

  • 分支预测器：程序里有大量 if 和循环，CPU 要提前猜下一条指令在哪，好提前取指。图里那张表记着每条分支指令最近几次跳没跳，按此预测下一次。
  • 乱序执行窗口：同时盯着几百条指令。图里第 1 条 ld（从内存读数）在等数据，第 2、3 条和它无关，就先执行完了，不必干等。
  • 大缓存：L1、L2，再加上十几个核心共用的 L3，让多数读取不必等到主内存。

这三样东西都是为了一件事：让同一条线程少停顿、早点算出结果。这对一般程序很要紧——你点一下按钮，希望马上有反应。可如果缓存没命中、乱序窗口里也找不到别的事可做，这条线程照样只能停下等内存。

再看 GPU 里的一个 SM（Streaming Multiprocessor，流式多处理器）。它是 GPU 里的一组运算通道，连同指挥它们的电路；H100 有 132 个 SM，第 2 节会看到它们怎样排在芯片上。左栏 ① 第二步放大了 SM 的四分之一，叫一个分区，四个分区一模一样。分区里最多的是两样东西：

  • 32 条 FP32 运算通道：每条通道每个周期能做一次 float32 运算。
  • 寄存器堆：64 KB，16 384 个 32 位寄存器。

调度器每个周期发出一条指令，这条指令同时送到 32 条通道，32 条通道各算各的数。比如 r2 ← max(r1, 0)，32 个线程各用自己寄存器 r1 里的数，各写各的 r2。这里的线程是 GPU 程序里的一条执行流，每个线程负责一份数据（这里一个线程管一个数），和操作系统里的线程不是一回事。同时接受同一条指令的 32 个线程编成一组，叫一个 warp。

为什么要 32 个一组？因为这样 32 条通道只需要一份取指、调度的电路。CPU 每个核心都要一整套分支预测、乱序执行电路；SM 把这些省掉，省下的面积全用来放运算通道和寄存器。整块 H100 有 132 × 4 × 32 = 16 896 条 FP32 通道，做 float32 运算约 67 TFLOP/s；一台桌面 CPU 约 2 TFLOP/s。

1.3 等内存的时候，两边怎么办

省掉乱序执行，GPU 等内存的时候怎么办？从显存读一次数据要约 350 ns，也就是约 700 个周期。

左栏 ① 第三步把两边放在同一条时间轴上（中间断开，省略了 10–350 ns 这一段等待）。CPU 线程发出读请求后，缓存没命中、又没有别的事可做，就停着，一直等到 350 ns 数据回来。

SM 的办法是让很多组线程同时住在 SM 上，轮流用通道。一个 SM 最多同时住 2048 个线程，也就是 64 个 warp，每个分区 16 个。W0 发出读请求后要等 350 ns，下一个周期调度器就给 W1 发指令，再下一个给 W2……这样 0.5 ns 换一个，16 个 warp 在 8 ns 内都发出了读请求。数据回来以后，再一个个算。

关键在于换 warp 不用保存任何东西。操作系统切换进程，要把 CPU 寄存器存到内存、再把另一个进程的读进来；SM 上 64 个 warp 的寄存器本来就同时放在寄存器堆里（这就是寄存器堆要 256 KB 那么大的原因），调度器只是改选下一个“数据已到”的 warp。

所以两边的思路不同：CPU 花大量电路让一条线程尽快完成；GPU 用大量常驻线程把等待的时间填满，追求的是单位时间完成的总计算量。这也说明了 GPU 的前提：要有成千上万份互不依赖的活。对 1678 万个数各自做 ReLU，正好如此。

不过左栏 ① 第三步也透露了 ReLU 的问题：16 个 warp 全在等，每个 warp 拿到数据后只做一次比较就完了，通道大部分时间闲着。这是本文开头那个“只跑出两千分之一”的伏笔，第 3、5 节会算清楚。

2. 一块 H100 里有什么

2.1 芯片平面：132 个 SM 和中间的 L2

🖼 请对照左栏 ②：一块 H100：芯片平面、数据的路、HBM 侧视（可交互）⧉ 单独打开

现在把一个个 SM 放回整颗芯片上（左栏 ② 第一步，按 NVIDIA 公布的结构重画，位置为示意，数量是实数）。

  • SM：每个小方格一个。完整的 GH100 芯片有 144 个 SM，每 18 个编成一组，叫 GPC（Graphics Processing Cluster），共 8 组。这只是物理上的分组，写程序时不用管。芯片做出来总有少数 SM 有缺陷，卖出去的 H100 SXM 屏蔽掉 12 个（灰色），只启用 132 个；不这样做，一颗芯片只要有一个坏 SM 就得报废，能卖的芯片会少很多。
  • L2 缓存：中间两条，共 50 MB，所有 SM 共用，作用和计组里的缓存一样。它分成左右两半，SM 读自己这一半快，读另一半要绕过去，大约慢一倍。
  • 内存控制器和 HBM：芯片左右两侧的竖条是内存控制器，连着芯片旁边的 HBM（High Bandwidth Memory，高带宽内存），也就是显存。
  • PCIe 接口和 GigaThread 引擎：上面一条。PCIe 是显卡和 CPU 之间的连接；GigaThread 引擎负责把一个 GPU 程序的工作分给各个 SM（第 3 节会看到它怎么分）。
  • NVLink：下面一条，连到同一台服务器里其他 GPU 的高速链路（CS336 第 7 讲讲多卡并行时才用到）。

2.2 数据的路：从主机内存到 SM

左栏 ② 第二步画了数据走的路。张量一开始在主机内存（CPU 那边的内存条）里，要先由 CPU 经 PCIe 搬进显卡的 HBM：PyTorch 里写 x.to("cuda") 就是这一步，PCIe 5.0 ×16 每个方向约 64 GB/s，64 MB 约 1 ms。之后 GPU 程序运行时，SM 需要的数从 HBM 经内存控制器、L2 送到 SM，HBM 的带宽是 3.35 TB/s，是 PCIe 的约 50 倍。

所以训练时数据一旦搬进显存，就尽量留在那里反复用；每一步都在主机和显卡之间来回搬，PCIe 会成为瓶颈。

2.3 HBM：DRAM 叠起来，贴在芯片旁边

HBM 为什么能比普通内存快那么多？左栏 ② 第三步从侧面剖开看。HBM 就是计组里的 DRAM，只是做法不同：

  • 8 层左右的 DRAM 芯片叠成一摞，用穿透每层硅片的竖直导线（TSV）连通，叫一个堆栈，每个 16 GB。
  • 堆栈和 GPU 芯片并排放在同一块硅转接板上，中间只隔几毫米，转接板上刻着上千根细导线，所以每个堆栈能拉出 1024 根数据线。

H100 SXM 用 5 个堆栈，共 80 GB，合计 5120 根数据线，带宽 3.35 TB/s。对照 CPU 的内存条：插在主板插槽里，离 CPU 十几厘米，每条通道只有 64 根数据线，带宽几十 GB/s。DRAM 还是那种 DRAM，快在接口极宽、离芯片极近。

🖼 请对照左栏 ③：H100 整颗芯片（NVIDIA 原图）⧉ 单独打开

左栏 ③ 是 NVIDIA 官方的 GH100 芯片结构图（深灰底、绿色块那张），引自 NVIDIA 技术博客《NVIDIA Hopper Architecture In-Depth》，这张图在讲 GPU 的地方随处可见。对照左栏 ② 看：最上面一条是 PCI Express 5.0 Host Interface 和 GigaThread Engine；8 个大框是 GPC，每个 GPC 里有 9 个 TPC（每个 TPC 是两个 SM 的组合）；中间两条浅蓝色带子是 L2 Cache；两侧是 Memory Controller 和 HBM3；最下面一排是 NVLink。

🖼 请对照左栏 ④：一个 SM 的内部（NVIDIA 原图）⧉ 单独打开

左栏 ④ 是同一篇博客里一个 SM 的内部图。4 个相同的分区，每个分区从上到下是：

  • L0 Instruction Cache / Warp Scheduler (32 thread/clk) / Dispatch Unit：指令缓存、warp 调度器和分发单元。“32 thread/clk”就是每个周期给一个 warp 的 32 个线程发一条指令。
  • Register File (16,384 × 32-bit)：寄存器堆，16 384 个 32 位寄存器，64 KB。
  • INT32 ×16、FP32 ×32、FP64 ×16：整数、单精度浮点、双精度浮点的运算通道。32 条 FP32 通道正好让一个 warp 的 32 个线程一个周期各做一次 float32 运算。
  • Tensor Core（第 4 代）：专门做矩阵乘的电路，下面单独讲。
  • LD/ST ×8：读写单元，负责发出访存请求。SFU：特殊函数单元，算 sin、cos、exp、倒数平方根这类函数。

4 个分区下面是全 SM 共用的部分：

  • Tensor Memory Accelerator（TMA）：专门在 HBM 和共享内存之间成块搬数据的硬件，Hopper 这一代新加的。
  • 256 KB L1 Data Cache / Shared Memory：一块 256 KB 的 SRAM，一部分当 L1 缓存（硬件自动管理，和 CPU 的 L1 一样），一部分当共享内存——程序自己决定往里放什么，同一组线程（第 3 节的“线程块”）可以通过它交换数据。
  • Tex：纹理单元，画图形用，训练模型时用不到。

2.5 Tensor Core：矩阵乘法有专门的电路

普通运算通道一条指令只做一次乘加。可神经网络里绝大部分计算是矩阵乘法，于是 NVIDIA 在每个分区里放了一个 Tensor Core：一条指令完成一个小矩阵的乘加 \(D = A\times B + C\)（例如一块 16×16 乘 16×16）。一个小矩阵乘加包含几千次乘法和加法，一条指令全做完，省下了逐条发指令的开销。

结果是两种运算的速度差得很远。H100 每个 Tensor Core 每周期大约能做 1024 次 bf16 浮点运算，而一个分区的 32 条 FP32 通道合起来每周期只做 64 次（32 次乘加）。所以 H100 用 Tensor Core 做 bf16 矩阵乘能到约 989 TFLOP/s，用普通通道做 float32 运算只有约 67 TFLOP/s：矩阵乘法比其他运算快十几倍。开头那个 989，指的就是这个；后面所有优化思路都从这里出发——尽量把计算变成矩阵乘，让 Tensor Core 有活干。

用显卡做矩阵乘由来已久：2001 年 Larsen 和 McAllister 的论文《Fast Matrix Multiplies using Graphics Hardware》就把矩阵存成纹理，借当时只能画图的可编程着色器算矩阵乘。真正的分岔出现在 2017 年的 V100：CS336 有一张图，从 K80、M60 到 P100，矩阵乘和其他运算的算力几乎一样（都在 10 TFLOP/s 上下）；V100 引入 Tensor Core 后，矩阵乘一下跳到约 125 TFLOP/s，其他运算约 15；A100 是 312 对 19.5；H100 是 989 对 67。

3. 一个 GPU 程序是怎么跑起来的

硬件看完了，现在看软件怎样用它。用 y = torch.relu(x) 从头走一遍：从 Python 里一行代码，到 GPU 上 1678 万个数全部处理完。

🖼 请对照左栏 ⑤：一次 ReLU kernel（可交互）⧉ 单独打开

左栏 ⑤ 是交互演示，分四幕。

3.1 启动：CPU 下命令，GPU 分块

kernel。 PyTorch 发现 x 在 GPU 上，就挑出一个事先写好、编译好的 GPU 程序来算。在 GPU 上运行的函数叫 kernel。kernel 的写法和普通程序不同：它写的是“一个线程做什么”（左栏 ⑤ 第一幕第 1 步，左边的代码）：

i = blockIdx * 256 + threadIdx   // 我负责第几个数
v = x[i]
y[i] = max(v, 0)

要处理 16 777 216 个数，就开 16 777 216 个线程，每个线程用自己的编号 i 处理一个数。为什么这样写？因为 GPU 要的就是成千上万份独立的活（第 1.3 节），按线程来写，硬件怎样把线程分给通道就不必程序员操心。

命令和异步。 CPU 这边，CUDA 驱动（CUDA 是 NVIDIA 的 GPU 编程平台；驱动是显卡的驱动程序，在 CPU 上运行）把“跑哪个 kernel、开多少线程、x 和 y 在显存里的地址”写成一条命令，放进命令队列，通知 GPU（第 2 步）。Python 并不等 GPU 算完，torch.relu 立刻就返回了，接着执行下一行，这叫异步执行。准备这条命令约 2–5 µs。只有当 Python 真正要用 y 的值（打印、.item()、搬回 CPU）时，CPU 才停下来等 GPU 算完。

线程块和 grid。 1678 万个线程不会直接扔给硬件，而是每 256 个编成一组，叫一个线程块（block）。块 b 负责 x[256b] 到 x[256b+255]，代码里的 blockIdx 就是块号，threadIdx 是块内第几个线程（0–255）。\(16\,777\,216 \div 256 = 65\,536\) 个块，全部块合起来叫一个 grid（第 3 步）。

为什么要有“块”这一层？因为一个块从头到尾只在一个 SM 上运行，块里的线程能通过这个 SM 的共享内存交换数据、互相等待（第 6.6 节分块矩阵乘就靠这一点）；不同块之间做不到。ReLU 用不上这个能力，但写法是一样的。

分给 SM。 GPU 上的 GigaThread 引擎拿到命令后，把块分给各个 SM（第 4 步）。一个 SM 最多同时住 2048 个线程，也就是 8 个这样的块。132 个 SM 先各拿 8 个：SM 0 拿到块 0、132、264……，共 1056 个块上了 SM，其余 64 480 个排队。

3.2 一个 warp 怎样执行

第二幕把镜头拉近到 SM 0，时间单位换成纳秒。

块到了 SM 上，再按线程号每 32 个切成一个 warp：线程 0–31 是 warp 0，32–63 是 warp 1……一个块 8 个 warp，分到 4 个分区；分区 0 拿到每个块的第 0 号和第 4 号 warp，8 个块共 16 个，演示里叫 W0–W15（第 1 步）。W0 是块 0 的线程 0–31，负责 x[0..31]。

调度器挑中 W0，发出“算下标”这条指令（第 2 步）：32 个线程同时执行同一条指令，但每个线程用的是自己寄存器里的线程号，算出 0、1、2……31 各不相同。一条指令、32 个线程、各自的数据，这种执行方式叫 SIMT（Single Instruction, Multiple Threads，单指令多线程）。

接着 W0 发出“读 x[i]”（第 3 步）。32 个线程要读的地址是 0x7000_0000、0x7000_0004……0x7000_007C，正好连续 128 字节。读写单元把它们合并成一次 128 字节的请求（为什么这很重要，第 6.5 节讲）。L1 没有，L2 也没有，请求发到 HBM。约 350 ns 后才有回音，W0 只能等。

下一个周期调度器就换 W1 发指令，再下一个换 W2……（第 4 步）。大约 8 ns 后，16 个 warp 全发出了读请求，全在等。ReLU 每个元素只做一次比较，没有别的活可干——这个 kernel 的时间注定大部分花在等内存上。

约 350 ns 后数据到了，32 个数分别落进 W0 的 32 个线程的寄存器 r1，W0 重新就绪（第 5 步）。一条“取较大值”指令，32 条通道一个周期算完：−3、2、−1、5 变成 0、2、0、5（第 6 步）。然后写回 y[i]，地址同样连续，合并成一次 128 字节的写（第 7 步）。

3.3 分支发散：if/else 在 warp 里怎么走

第三幕看一种常见的写法问题。如果 kernel 写成 if (x < 0) y = 0; else y = x;，同一个 warp 里，x 为负的线程要走 if，其余的走 else。可一个 warp 一次只能执行一条指令，怎么办？

硬件用一个 32 位的活动掩码，一位对应一个线程。先把 x<0 的线程对应的位置 1，执行 y = 0，掩码为 0 的通道空转；再把掩码取反，执行 y = x，这回刚才干活的空转。两条路的时间加在一起，这叫分支发散（control divergence）。CS336 的例子是 if (threadIdx.x < 4) { A; B; } else { X; Y; } Z;：线程 0–3 执行 A、B 时，其余 28 个线程空等；28 个线程执行 X、Y 时，线程 0–3 空等；到 Z 才重新一起走。

它不会算错，只是比在 CPU 上代价大；能写成 max、select 这类没有分支的形式更好，或者让同一个 warp 的线程走同一条路。

3.4 全部跑完：时间花在哪

第四幕。一个块的 8 个 warp 都结束后，SM 空出位置，GigaThread 引擎立刻补上队首的块 1056。65 536 个块，每轮约 1056 个，大约轮 62 次。

现在可以算账了。读 x 64 MB、写 y 64 MB，共 128 MB，HBM 每秒最多搬 3.35 TB：

\[t \ge \frac{128\ \text{MB}}{3.35\ \text{TB/s}} \approx 38\ \mu\text{s}\]

38 µs 里只做了 1678 万次比较，折合 0.44 TFLOP/s，而 FP32 通道的峰值是 67 TFLOP/s：运算通道 99% 以上的时间在等数据。这就是开头那个问题的答案：ReLU 的速度由 HBM 带宽决定，和有多少运算通道无关。同样 128 MB 在内存带宽约 90 GB/s 的 CPU 上要约 1.4 ms，GPU 快约 37 倍，正好是两边内存带宽之比。

反过来，张量很小时，GPU 几微秒就算完，时间全花在每次 2–5 µs 的启动开销上——由很多小运算组成的模型在 GPU 上跑不快，原因就在这里。

占用率。 第三步还交代了一个限制。每个线程最多能用 255 个寄存器，用得越多，一个 SM 能同时住的线程就越少。CS336 第 6 讲的例子：一个块 64 个线程，每个线程用 160 个寄存器，一个 SM 的寄存器堆有 65 536 个寄存器，那么最多住 \(\lfloor 65\,536 \div (64\times160) \rfloor = 6\) 个块、384 个线程，只有满额 2048 个的不到五分之一。实际住的 warp 数占满额的比例叫占用率。住的 warp 少了，等内存时可换的就少，通道更容易闲着。占用率低也不一定坏：如果每个线程多处理几个元素（叫 thread coarsening，例如用 Triton——一种写 kernel 的语言，见现状更新——编出的 GeLU 每个线程一次处理 8 个元素；GeLU 是和 ReLU 类似的另一种激活函数），线程少一些也能把通道喂饱。

4. 存储层次：数据离运算通道有多远

第 3 节看到，一次 HBM 访问要约 700 个周期，ReLU 的时间几乎全耗在这上面。GPU 和 CPU 一样有一整层存储，越靠近运算通道越快、越小。想让程序快，就得知道每一层在哪、多大、多快、谁能用。

带宽差得同样悬殊：整颗芯片的寄存器合计约 400 TB/s，共享内存合计约 33 TB/s，L2 约 12 TB/s，HBM 3.35 TB/s，PCIe 每个方向约 64 GB/s。为什么不把 HBM 都换成快的 SRAM？CS336 第 5 讲给的对比是：SRAM（共享内存、缓存用的那种存储）比 DRAM（HBM）每字节贵约 100 倍，快约 8 倍。所以只能在近处放一点贵而快的，远处放大量便宜而慢的，和计组里 Cache—主存的道理一样。

“谁能看见”这一列最要紧（左栏 ⑥ 第二步）。同一个线程块的线程在同一个 SM 上，可以通过共享内存交换数据，也可以互相等待（同步）；不同线程块可能在不同 SM 上，它们之间交换数据只能写到 L2/HBM 再读出来，慢得多。第 6.6 节的分块、第 7 节的 FlashAttention，都是在利用“块内共享内存”这一层。

CUDA 编程手册的内存模型里还有两种名字容易误导的存储。local memory（局部内存）是每个线程私有的，但它其实放在 HBM 里：线程要用的寄存器太多、塞不下时，编译器把一部分变量“溢出”到这里，所以它一点也不快。constant memory（常量内存）是整个 grid 只读的一小块（64 KB），也在 HBM 里，但有专门的缓存，一个 warp 的线程读同一个地址时很快。CPU 上的程序能直接碰到的只有 global memory（就是 HBM）和 constant memory：把数据搬进、搬出它们。

延迟的具体数字，不同测法相差不小。CS336 第 5 讲用的是一张 A100（H100 的上一代）的实测表（单位是周期）：global memory 约 290、L2 约 200、L1 约 33、共享内存读约 23、写约 19。上表 H100 的 HBM 约 700 个周期，来自 Chips and Cheese 用一长串前后依赖的读取测出的结果，包含了地址翻译等开销。两组数字的量级关系一样：共享内存和 L1 比 HBM 快一个数量级。同一页还放了 A100 的芯片照片（Locuza 标注）：完整的 GA100 有 128 个 SM、8192 条 FP32 通道、48 MB L2（分成两个 24 MB 的分区，正是左栏 ③ 里那两条浅蓝带子的位置），四周是 6144 位宽的 HBM2(e) 接口，芯片面积约 826 mm²。

5. 快慢由什么决定

5.1 算力涨得比内存带宽快

ReLU 慢在搬数据，这不是特例。CS336 第 5 讲的一张图（引自 Gholami 等人的《AI and Memory Wall》）显示：过去二十年，硬件的峰值算力涨了约 6 万倍（每两年 3.0 倍），DRAM 带宽只涨了约 100 倍（每两年 1.6 倍），芯片之间的互连带宽约 30 倍（每两年 1.4 倍），差距越拉越大。H100 上，Tensor Core 每秒能做 989 万亿次 bf16 运算，HBM 每秒只能送 3.35 万亿字节。

所以一个 kernel 跑得慢，先要问慢在哪。它的时间可以拆成三份（Horace He《Making Deep Learning Go Brrrr》的说法）：真正做运算的时间、在 HBM 和 SM 之间搬数据的时间，以及其他一切开销（Python 解释、PyTorch 分派、每次几微秒的启动）。哪一份最大，就该优化哪一份：搬数据最慢时，再快的 Tensor Core 也帮不上忙；开销最大时，改算法也没用。

5.2 屋顶线：一眼看出卡在算还是卡在搬

怎样判断一个运算卡在哪？看它的算术强度：每从 HBM 搬 1 字节，做几次浮点运算（单位 FLOP/字节）。ReLU 每读 4 字节、写 4 字节，只做 1 次比较，强度是 \(1/8\)。

🖼 请对照左栏 ⑦：屋顶线⧉ 单独打开

左栏 ⑦ 是 H100 的屋顶线图，横轴是算术强度，纵轴是能达到的速度，两个轴都是对数刻度。一个 kernel 的速度受两样东西限制：HBM 每秒只能送 3.35 TB，按强度换算成运算就是一条斜线；Tensor Core 最多 989 TFLOP/s，是一条平线。实际速度不超过两条线中较低的那条：

\[\text{速度} \le \min\left(\underbrace{3.35\ \text{TB/s} \times \text{算术强度}}_{\text{斜线：HBM 能喂多快}},\ \underbrace{989\ \text{TFLOP/s}}_{\text{平线：Tensor Core 峰值}}\right)\]

两条线在 \(989 \div 3.35 \approx 295\) FLOP/字节处相交，这是拐点：每搬 1 字节至少要做 295 次运算，Tensor Core 才可能被喂饱。图中绿色虚线是不用 Tensor Core 的 FP32 峰值 67 TFLOP/s。

图上的点就是本文的几个例子（紫色的两个 sin²+cos² 点在第 6.3 节讲）：

  • ReLU（float32）：强度 \(1/8\)，最多 \(3.35 \times 1/8 \approx 0.42\) TFLOP/s——就是第 3 节算出的那个数。
  • 矩阵乘 \(N\times N\)（bf16）：做 \(2N^3\) 次运算（\(N^2\) 个输出，每个是 \(N\) 次乘加），最少搬 \(3N^2\) 个数（读两个输入、写一个输出），每个 2 字节，强度 \(\dfrac{2N^3}{6N^2} = N/3\)。\(N = 128\) 时只有 43，仍在斜线下；\(N = 4096\) 时是 1365，顶到平线。所以大矩阵乘是 GPU 上少数能跑满算力的运算，矩阵太小反而受带宽限制。这回答了开头的第二个问题。

点落在斜线段，叫受内存带宽限制（memory-bound），想快只能少搬字节；落在平线段，叫受算力限制（compute-bound）。

CS336 的屋顶线图上还有几条更高的斜线：数据已经在共享内存里时，上限是 33 TB/s × 强度；在寄存器里时约 400 TB/s × 强度（左栏 ⑦ 的蓝、紫虚线）。数据离运算通道越近，同样的强度能跑得越快，拐点也越靠左——第 6.6 节的分块就是把数据挪到这几条线上。灰虚线是一台桌面 CPU（内存约 90 GB/s、约 2 TFLOP/s，估算），整体低一到两个数量级。CS336 图上还标了稠密和稀疏两类矩阵乘：稀疏矩阵乘要额外搬下标、每个数被复用的次数少，强度低，落在斜线段。

下面六个办法，第一个和内存无关，后五个都是在少搬字节，或者把数据留在离通道更近的那一层。

6. 让它快起来的办法

6.1 避免分支发散

第 3.3 节已经看过：一个 warp 里的线程走不同的分支，就要分几遍执行。办法是尽量写成没有分支的形式，或者让同一个 warp 的线程走同一条路。

6.2 低精度：每个数少占几个字节

ReLU 卡在搬字节上。最直接的办法是让每个数少占几个字节。同一个 ReLU 改用 bf16（每个数 2 字节）：读 2 字节、写 2 字节，强度从 \(1/8\) 变成 \(1/4\)，左栏 ⑦ 上的点右移一倍，时间减半。代价是每个数能表示的精度和范围变小，所以要知道各种格式丢了什么。

🖼 请对照左栏 ⑧：低精度⧉ 单独打开

左栏 ⑧ 最上面把同一个数 3.14159 存进六种格式，每格是一位：红色是符号位，蓝色是阶码（管能表示多大多小），绿色是尾数（管精度）。这和计组里 IEEE 754 的结构一样，只是位数不同。

  • FP32（1+8+23 位）存成 3.1415901；BF16（1+8+7）和 FP16（1+5+10）都存成 3.140625。BF16 的阶码和 FP32 一样宽，所以范围相同、精度差；FP16 尾数多一些，但阶码只有 5 位，最大只能表示 65504，训练中大一点的梯度会溢出（梯度：训练时算出的“每个参数该往哪个方向改、改多少”，第 6.4 节有例子）。训练里现在多用 BF16。
  • 8 位浮点有两种：E4M3（4 位阶码、3 位尾数）把 3.14159 存成 3.25，最大 448；E5M2 存成 3.0，范围更大、更粗。
  • 4 位的 E2M1 一共只有 0、±0.5、±1、±1.5、±2、±3、±4、±6 这 15 个值（+0、−0 各占一个码，共 16 个码），3.14159 只能存成 3。

精度丢了，算出来的结果还能用吗？左下是 Tensor Core 的做法：两个 bf16 输入相乘，乘积不舍入，加进一个 FP32 的累加器，最后输出 FP32。输入用 16 位是为了搬得少；累加用 32 位，是因为一次矩阵乘要把几千个乘积加在一起，16 位的累加器会把小的乘积舍掉。

哪些运算能放心用 16 位？右下是 CS336 引用的 NVIDIA 混合精度教程的分类：矩阵乘和大多数逐元素运算（relu、tanh、加减乘）可以用 16 位存；“把小数加进大和”的运算要 FP32 的精度，比如求和、softmax 的分母、各种归一化；输出远大于输入的运算（exp、log、pow）和损失函数要 FP32 的范围。

位数再少，一个格式的范围就不够用了。办法是让一小组数共用一个缩放因子：存的是“缩放因子 × 元素”。Blackwell（H100 的下一代）支持的 MXFP8 是每 32 个 E4M3 数共用一个 E8M0 缩放因子（只有 8 位阶码，就是一个 2 的幂次），左栏 ⑧ 最下面画了三组，各自乘 \(2^{-3}\)、\(2^{5}\)、\(2^{0}\)。一组里的数大小差不多，共用一个幂次就够，不同组可以差很远。因为有了缩放因子，元素就选精度更好的 E4M3，而不用范围更大的 E5M2。NVIDIA 的 NVFP4 走得更远：每 16 个 E2M1 数配一个 E4M3 缩放因子。

CS336 引的 MXFP8 训练论文（arXiv 2506.08027）给出了实际流程。先交代几个训练的词：模型里要学的参数矩阵叫权重（就是 x @ W 里的 W）；每一层算出来、传给下一层的数叫激活值；训练一步先做前向传播（从输入一层层算到损失），再做反向传播（从损失往回，算出每个权重的梯度），最后由优化器按梯度更新权重。训练一步要做三类矩阵乘：前向传播算输出（FPROP），反向传播求输入的梯度（DGRAD）和求权重的梯度（WGRAD）。权重和梯度的“主副本”仍用 BF16/FP32 保存；FPROP 把权重和激活值量化成 MXFP8 再算；DGRAD、WGRAD 也用 MXFP8，但它们要用到矩阵的转置，转置后“32 个一组”的方向变了，所以要从 BF16 重新量化一份转置，不能直接把量化好的矩阵转过来；DGRAD 的结果以 BF16 传给前一层，WGRAD 的结果以 FP32 交给优化器去更新主副本。也不是所有运算都量化：一个 Transformer 块（大语言模型的基本组成单元）里只有 QKV 投影、输出投影和前馈层的两个全连接（FC1、FC2）这几个带权重的矩阵乘用 MXFP8；注意力内部的两次矩阵乘（\(QK^\top\) 和乘 \(V\)，第 7 节）、softmax、LayerNorm（一种归一化）、残差相加仍用 BF16。这些名字不必都记住，要点是：带权重的大矩阵乘用 8 位，其余对精度敏感的部分保留 16 位。H100 上 bf16 约 989 TFLOP/s，FP8 约 2000 TFLOP/s。

6.3 算子融合：中间结果不回 HBM

🖼 请对照左栏 ⑨：融合与重算⧉ 单独打开

看一个比 ReLU 稍复杂的例子（左栏 ⑨ 上半，CS336 的例子）：\(y = \sin^2 x + \cos^2 x\)。按 PyTorch 一个函数一个函数地执行，要启动 5 个 kernel：sin、cos、平方、平方、相加。每个 kernel 都从 HBM 读输入、把结果写回 HBM，下一个再读回来。x 是 64 MB 的 float32 时，一共读写 11 个 64 MB 的张量 = 704 MB，约 210 µs，加上 5 次启动约 225 µs。

问题出在中间结果：sin x 算出来，写进 HBM，紧接着又被读出来平方。如果把 5 步写进同一个 kernel（融合）：每个线程读一次 x[i]，在自己的寄存器里算 sin、cos、平方、相加，写一次 y[i]。只搬 128 MB，约 38 µs，加一次启动约 41 µs，快 5 倍多，结果一字不差。中间值从不进 HBM。图上时间轴里，每条前面的空隙是启动开销，条的长度是搬数据的时间——运算本身快到可以忽略。左栏 ⑦ 上，两个紫点就是融合前后：融合后强度变高，点沿斜线右移。

这种逐元素的融合编译器能自动做，torch.compile（PyTorch 把一段 Python 代码编译成 GPU kernel 的功能）生成的就是融合好的 kernel（CS336 第 6 讲用性能分析工具看到：手写的 GeLU 启动了好几个 kernel，内置版和编译版都只有一个）。所以融合之后，gelu 和 relu 耗时几乎一样——都是读一次、写一次。

6.4 重算：宁可多算，也不多搬

左栏 ⑨ 下半先要说明：训练时反向传播为什么要用前向的中间结果。CS336 借用 CS221 的例子：\(\text{Loss}(x,y,w) = (w\cdot\phi(x) - y)^2\)（\(w\) 是权重，\(\phi(x)\) 是输入 \(x\) 的特征向量，\(y\) 是正确答案，Loss 是平方误差），取 \(w = [3,1]\)，\(\phi(x) = [1,2]\)，\(y = 2\)。前向从叶子往根算：\(\text{score} = w\cdot\phi(x) = 5\)，\(\text{residual} = 5 - 2 = 3\)，\(\text{loss} = 3^2 = 9\)。反向从根往叶子算：\(\partial\,\text{loss}/\partial\,\text{residual} = 2\times3 = 6\)，\(\nabla_w \text{Loss} = 6\,\phi(x) = [6, 12]\)。反向用到了前向算出的 residual = 3 和 \(\phi(x)\)，所以前向的中间值要么存着，要么到时候重算。

存着就要搬数据。把三个 sigmoid 叠在一起，旧做法是前向时把中间结果 s1、s2 写进 HBM 存着：前向读 x、写 s2、s1、out，反向读 s2、s1、dout、写 dx，共 8 次 HBM 读写（dout 是损失对输出 out 的梯度，从后一层传来；dx 是要算出的、损失对输入 x 的梯度）。

新做法是前向时不存中间结果，反向时从 x 重新算一遍 sigmoid：前向读 x、写 out，反向读 x、dout、写 dx，共 5 次，访存只剩 5/8。多出来的 3 次 sigmoid 在寄存器里算，几乎不花时间。在受带宽限制的地方，多算一点换少搬一点是划算的。“激活检查点”（activation checkpointing）用的是同一个思路，主要目的是省显存。

6.5 合并访存与 bank 冲突：每次搬运别浪费

🖼 请对照左栏 ⑩：合并访存与 bank 冲突⧉ 单独打开

第 3.2 节说过，W0 的 32 个地址连续，读写单元把它们合并成一次 128 字节的请求。为什么这很重要？左栏 ⑩ 上半回到“读 x”这个动作。HBM 是 DRAM，计组讲过：DRAM 读一行要先激活整行到灵敏放大器里，所以一次读给的是连续的一大段（突发传输）。GPU 上，一个 warp 的 32 个线程同时访存，地址落在同一个 128 字节段里，就合成一次传输；散在 32 个段里，就要 32 次传输，每段 128 字节只用 4 字节，有效带宽剩 1/32。x 按行存，第 i 行第 j 列的地址是起点 + (i×4096 + j)×4：

  • 线程 k 读 x[0][k]：32 个地址连续，1 次传输，这就是合并访存（coalesced）。
  • 线程 k 读 x[k][0]：相邻线程的地址差一整行 \(4096\times4 = 16\) KB，32 次传输。

32 个线程 × 4 字节正好 128 字节，warp 是 32 个线程不是偶然。CS336 用一个 16 字节的玩具地址空间说明突发：每 4 字节一个突发段，访问第 0 号字节，0–3 号会一起送来；一个 warp 的访问全落在同一个段里，DRAM 只需一次请求。

矩阵乘里就会撞上这个问题。算 \(P = MN\)（都按行存）时，如果让线程 \(i\) 负责输出的第 \(i\) 行，第 \(k\) 步线程 \(i\) 读 \(M[i][k]\)：相邻线程读的是相邻行的同一列，地址差一整行，不合并。如果让线程 \(j\) 负责第 \(j\) 列，第 \(k\) 步读 \(N[k][j]\)：相邻线程读同一行相邻的数，合并。所以要让相邻线程负责输出的相邻列，或者先把整块数据搬进共享内存（第 6.6 节）。

共享内存也有自己的规矩（左栏 ⑩ 下半，CS336 第 6 讲）。它分成 32 个 bank（存储体），每个 4 字节宽，连续的 4 字节字依次落在 bank 0、1、2……31、0、1……同一个周期里，每个 bank 只能给一个地址供数。一块 32×32 的 float32 放进去，第 r 行第 c 列落在 bank \(c\)：读一行，32 个线程落在 32 个 bank，一个周期读完；读第 0 列，32 个线程全落在 bank 0，只能排队读 32 次——“32 路 bank 冲突”。办法是每行多留一个空位（存成 33 列，第 r 行第 0 列就落在 bank r），或者按“行号异或列号”重新排列（swizzling）。矩阵乘里一个矩阵按行读、另一个按列读，躲不开这个问题，所以高性能 kernel 都会处理它。

6.6 分块：把数据留在共享内存里反复用

这是 CS336 说的“最重要的一招”，也是矩阵乘能跑到屋顶线平线上的原因。

先看不分块的矩阵乘有什么问题。算 \(C = AB\) 时，C 的每个元素是 A 的一行和 B 的一列的点积。C 的第 0 行有 \(N\) 个元素，每个都要用 A 的第 0 行，于是 A 的第 0 行被读了 \(N\) 遍；如果每次都去 HBM 读，搬运量就是理论最少的 \(N\) 倍。

🖼 请对照左栏 ⑪：分块矩阵乘（可交互）⧉ 单独打开

左栏 ⑪ 是交互演示，用 4×4 的小矩阵算 \(C = AB\)，只看负责 C 左上角 2×2 的那个线程块，它有 4 个线程，每个线程算 C 的一个元素，累加值放在自己的寄存器 acc 里。右上角一直数着“这个块从 HBM 读了几个数”。

第 ① 幕：不分块。 每个线程自己算一个点积，要哪个数就去 HBM 读：线程 (0,0) 依次读 A[0][k] 和 B[k][0]（k = 0…3），acc 从 1 加到 4，读了 8 次。4 个线程一共读 32 次，可涉及的不同数字只有 16 个——A 的第 0 行被线程 (0,0) 和 (0,1) 各读了一遍，B 的第 0 列被 (0,0) 和 (1,0) 各读了一遍。推广到 \(N\times N\)：A 的每个数会被读 \(N\) 次。

第 ② 幕：分块。 把 k 方向切成长度 \(T = 2\) 的两段。第一段：4 个线程每人从 HBM 搬 A、B 各一个数，凑成 A[0..1][0..1]、B[0..1][0..1] 两个 2×2 小块，写进共享内存（8 次 HBM 读）；然后用 __syncthreads() 同步，等 4 个线程都搬完，否则有的线程会读到还没写进去的数——同步只能在一个线程块内部做，这正是“块”这一层存在的理由（第 3.1 节）。接着每个线程只读共享内存，做两次乘加，得到部分和 1、2、5、6。第二段再搬 A[0..1][2..3]、B[2..3][0..1]（又 8 次），算完得到 C = 4、5、12、13，和不分块完全一样。

HBM 读取从 32 次降到 16 次，正好少了 \(T\) 倍：每个数只从 HBM 搬进来一次，之后在共享内存里被需要它的线程反复用。一般地：

\[\text{每个输入从 HBM 读的次数：}\quad \underbrace{N}_{\text{不分块}} \;\longrightarrow\; \underbrace{N/T}_{\text{分块}}\]

\(N = 4096\)、\(T = 128\) 时，从 4096 次降到 32 次。而且搬小块时相邻线程读相邻地址，访存也是合并的。真实的矩阵乘 kernel 块边长取 64、128 或更大，块内的乘加交给 Tensor Core。块边长受几样东西制约：共享内存的大小（一个 SM 只有 256 KB）、合并访存的要求，以及矩阵边长能不能被块边长整除——最后这一条带来下一节的麻烦。

左栏 ⑬ 把三个原因画成具体的块：

  • wave 量化（上半）：块大小 256×128，A100 有 108 个 SM，每个 SM 一次算一块。1792×1792 的输出切成 \(7\times14 = 98\) 块，98 ≤ 108，一轮跑完；1793×1793 要切成 \(8\times15 = 120\) 块（多出来的最后一行块只有 1 行、最后一列块只有 1 列），第一轮跑 108 块，第二轮只有 12 块，其余 96 个 SM 闲着。工作量只多了 0.1%，实测速度从约 60 TFLOP/s 掉到约 43 TFLOP/s——左图里的锯齿就是这个。H100 有 132 个 SM，道理相同；CS336 第 6 讲给的办法是让块数能被 SM 数整除。
  • tile 量化（左下）：用 128×128 的块铺输出矩阵。256×256 正好 4 块，全满；256×257 要 \(2\times3 = 6\) 块，多出的 1 列就要再开 2 个块，这 2 块只有 1/128 有用，却和满块一样占一个 SM 算完整一轮（NVIDIA 矩阵乘性能指南里的例子）。
  • 对齐（右下）：每行 2048 个 float32 时，第 1 行从第 8192 字节开始，正好是一个 128 字节段的开头，一个 warp 读这一行前 64 个数（256 字节）正好 2 段、2 次传输；每行 2047 个时，第 1 行从第 8188 字节开始，落在上一段的末尾，同样 256 字节跨 3 段、3 次传输，而且以后每一行的起点都错开不同的量。

所以训练时常把维度凑成 64、128 的倍数，必要时补零（padding）。Karpathy 在 2023 年 2 月发过一条：把 nanoGPT 的词表从 50257 补到 50304（最近的 64 的倍数），整体提速约 25%，是当时最显著的一次优化——补出来的那几十个“词”从不使用，却让矩阵乘换上了快得多的 kernel。

7. FlashAttention：把前面的办法用在注意力上

7.1 注意力是什么，慢在哪

大语言模型处理一段文字时，先把它切成 \(N\) 个词元（token，大致是一个词或一个字），每个词元表示成一个 \(d\) 维向量。注意力这一步让每个词元去“看”其他所有词元：对第 \(i\) 个词元，用它的查询向量 \(q_i\) 和每个词元的键向量 \(k_j\) 做点积，得到 \(N\) 个分数，分数越大表示越相关；用 softmax 把分数变成加起来等于 1 的权重；再用这些权重对所有词元的值向量 \(v_j\) 加权平均，得到输出。所有词元一起写成矩阵就是

\[O = \mathrm{softmax}\!\left(QK^\top/\sqrt d\right)V\]

其中 \(Q\)、\(K\)、\(V\) 都是 \(N\times d\) 的矩阵，每行是一个词元的查询、键、值。三次运算：两次矩阵乘中间夹一个 softmax。softmax 对一行分数 \(s_1,\dots,s_N\) 算 \(e^{s_i}/\sum_j e^{s_j}\)。

问题出在中间：分数矩阵 \(S = QK^\top/\sqrt d\) 和概率矩阵 \(P = \mathrm{softmax}(S)\) 都是 \(N\times N\) 的。标准做法把它们写进 HBM 再读出来，\(N\) 翻倍，这部分的搬运量就变 4 倍；而 softmax 本身是逐元素运算，强度很低，落在屋顶线的斜线段。FlashAttention（Dao 等，2022）让注意力快了好几倍，用的正是第 6 节的分块、融合和重算。

🖼 请对照左栏 ⑭：FlashAttention 论文图 1（原图）⧉ 单独打开

左栏 ⑭ 是论文的图 1（原图，引自 Dao 等《FlashAttention》，GitHub 仓库 Dao-AILab/flash-attention）。左边是 A100 的存储层次：片上 SRAM（各 SM 的共享内存合计）约 20 MB、19 TB/s；HBM 40 GB、1.5 TB/s；CPU 内存超过 1 TB，但只有 12.8 GB/s。中间是算法：外层循环把 \(K^\top\)、\(V\) 按块搬进 SRAM（橙色小块），内层循环把 \(Q\) 的块搬进来，在 SRAM 里算出这一块的 \(QK^\top\)，处理完把输出写回 HBM，\(N\times N\) 的大矩阵（虚线框）从不完整地出现。右边是 GPT-2 上一次注意力的耗时：PyTorch 的做法约 17 ms，其中两次矩阵乘只占一小部分，dropout（训练时随机把一部分值置零）、softmax、mask（把不该看的位置，比如后面的词，屏蔽掉）这些逐元素运算各占好几毫秒——它们都受内存带宽限制；FlashAttention 把这些融合成一个 kernel，约 2 ms。

论文里的另一组数字（GPT-2 medium，A100）：标准注意力做 66.6 GFLOP、读写 HBM 40.3 GB、用时 41.7 ms；FlashAttention 做 75.2 GFLOP——反而多了，因为反向时要重算——但只读写 4.4 GB，用时 7.3 ms。块越大，读写 HBM 的量越少，用时随之下降，块边长到 256 左右以后就降不太动了。运算多了 13%，搬的字节少了 9 倍，时间少了 5.7 倍：这就是第 5.2 节屋顶线的意思。

7.3 一行注意力，一步步算

🖼 请对照左栏 ⑮：FlashAttention（可交互）⧉ 单独打开

左栏 ⑮ 只看一个查询 q 那一行：它对 4 个键的分数是 2、1、3、0，值只看一维，是 10、20、30、40。

第 ① 幕：标准做法，3 个 kernel。 kernel 1 算出整张 S 写进 HBM；kernel 2 读 S，按行做 softmax：先找最大值 \(m = 3\)（减掉它是为了 \(e^x\) 不溢出，结果不变），算 \(e^{s-m} = 0.3679,\ 0.1353,\ 1,\ 0.0498\)，求和 1.5530，相除得 P = 0.2369、0.0871、0.6439、0.0321，写回 HBM；kernel 3 读 P 和 V，算出输出 24.71。\(N = 4096\)、bf16、一个注意力头时（模型把注意力分成几十份并行计算，每份叫一个头，各有自己的 Q、K、V），S 和 P 各 32 MB，在 HBM 里进出 4 趟（写 S、读 S、写 P、读 P），共 128 MB，H100 上约 38 µs，还占 64 MB 显存；每一层、每个头都来一遍。

第 ② 幕：FlashAttention。 键和值每次只搬 2 个进共享内存，分数只在寄存器里待一下。难点在 softmax：它要先知道一整行的最大值和总和，可分块时一次只看见一部分，后面的块里可能冒出更大的分数。解决办法是在线 softmax（Milakov 与 Gimelshein，2018）。普通的“安全 softmax”要扫三遍：第一遍找最大值 \(m\)，第二遍求 \(d = \sum_j e^{x_j - m}\)，第三遍算每个 \(e^{x_i - m}/d\)。在线版本把前两遍合成一遍，每读一个新数 \(x_j\) 就更新：

\[m_j = \max(m_{j-1},\, x_j),\qquad d_j = d_{j-1}\, e^{m_{j-1} - m_j} + e^{x_j - m_j}\]

最大值变了，就把旧的和乘一个 \(e^{m_{j-1}-m_j}\) 换到新基准上——这些因子一路相乘、相消（课上叫 telescoping sum）。FlashAttention 一次读一块而不是一个数，并顺带维护输出的累加值。具体维护三个数：目前见过的最大分数 \(m\)、\(l = \sum e^{s-m}\)、\(acc = \sum e^{s-m}\,v\)。

  • 第 1 块（分数 2、1）：\(m = 2\)，\(l = e^0 + e^{-1} = 1.3679\)，\(acc = 1\times10 + 0.3679\times20 = 17.358\)。
  • 第 2 块（分数 3、0）：出现更大的 3。前面的和都是按“减 2”算的，因为 \(e^{s-2}\times e^{2-3} = e^{s-3}\)，把旧的 \(l\) 和 \(acc\) 各乘一次 \(e^{2-3} = 0.3679\)，就换成了“减 3”的基准：\(l = 0.5032\)，\(acc = 6.386\)。再加上新块：\(l = 0.5032 + 1 + 0.0498 = 1.5530\)，\(acc = 6.386 + 30 + 1.991 = 38.377\)。
  • 最后除一次：\(38.377 \div 1.5530 = 24.71\)，和标准做法逐位相同。

整个过程是一个 kernel：\(QK^\top\) 的分块乘法、exp、求和、再乘 V 全部融合，HBM 里只出现输入 Q、K、V 和输出 O，\(N\times N\) 的 S 和 P 一次也没写进去。反向传播时，FlashAttention 也不存 P，而是按块重算——就是第 6.4 节的重算。

左栏 ⑯ 从外往里放大，把程序里的每一层放回它运行的硬件里：

  • 一个 kernel 占用整块 GPU，输入输出在 HBM 里，启动一次约 2–5 µs。
  • grid 的 65 536 个线程块，由 132 个 SM 轮流接手；块之间只能经 L2/HBM 交换数据。
  • 一个线程块住在一个 SM 上（同时最多 8 个），块内的线程共用共享内存、可以同步。
  • 一个 warp 的 32 个线程由一个分区的调度器带着，同一时刻执行同一条指令。
  • 一个线程在第（线程号 mod 32）条通道上算，用寄存器堆里自己的一份寄存器。

性能问题大多归结为：数据有没有放在离运算通道足够近的那一层。分块把数据从 HBM 提到共享内存，融合把中间结果留在寄存器里，低精度和重算减少要搬的字节，合并访存让每次搬运不浪费。CS336 第 5 讲的结论是：现在的 GPU 让人必须同时想着两件事——尽量把活变成矩阵乘，以及数据怎么搬。

和 TPU 比一比。 CS336 第 5 讲也顺带比较了 Google 的 TPU（Google 自己设计的、专做神经网络计算的芯片）：高层结构和 GPU 相似——控制逻辑简单、有很大的矩阵乘单元、有快速的片上存储；不同在于 TPU 的核心数少而每个更大，没有 warp 这一层（只有块），以及多芯片之间的连法（第 7 讲）。一个 TPU 核心里，标量单元（Scalar Unit）像 CPU 一样取指、给其他单元派活，向量单元（VPU）做逐元素运算，矩阵乘单元（MXU）做矩阵乘，向量存储（VMEM）是片上的快速存储。课上引用 JAX《How to Scale Your Model》的对照表：

GPU 的部件 TPU 里对应的 H100 的数量 TPU v5p 的数量
SM TensorCore（一个核心） 132 2
warp 调度器 VPU 的槽 528 8
共享内存 / L1 VMEM 共 32 MB 128 MB
寄存器 向量寄存器 共 32 MB 256 KB
Tensor Core MXU 528 8
HBM HBM 80 GB 95 GB

两者矩阵乘的算力相近，差别在于把它切成很多小核心（GPU）还是少数几个大核心（TPU）：小核心更容易处理矩阵乘以外的零碎运算，大核心做矩阵乘更省控制逻辑。AMD GPU 对应 warp 的单位叫 wavefront，传统上是 64 个线程。

  • Blackwell（B200）：2025 年起大量部署。148 个 SM，每个 SM 的结构和 H100 类似；HBM3e 192 GB，带宽约 8 TB/s；bf16 稠密约 2250 TFLOP/s，拐点约 281 FLOP/字节，和 H100 差不多——算力和带宽一起涨了约 2.3 倍。新增了专给 Tensor Core 用的 Tensor Memory（TMEM），位于寄存器和共享内存之间；硬件支持 MXFP8、MXFP4/NVFP4 这些带分组缩放的低精度格式（第 6.2 节）。L2 增大到约 126 MB。数据见 JAX《How to Scale Your Model》GPU 一章与 CS336 第 6 讲。
  • Rubin：NVIDIA 技术博客给出的参数是：两颗达到光刻尺寸上限的计算裸片拼成一颗 GPU，共 3360 亿个晶体管、224 个 SM、896 个 Tensor Core，HBM4 最多 288 GB、峰值带宽约 22 TB/s（Blackwell 的约 2.8 倍），NVFP4 算力最高 50 PFLOP/s，NVLink 6 每颗 GPU 3.6 TB/s。NVIDIA 于 2026 年 6 月在台北的 GTC 大会上宣布 Vera Rubin 平台全面投产，据报道 2026 年第三季度开始出货。
  • FlashAttention 从 2022 年的第一版起持续改写：第二版（2023）调整了线程块之间的分工，第三版（2024）专门利用 Hopper 的 TMA 和异步执行，此后又有针对 Blackwell 的版本；思路始终是本文第 7 节的分块 + 在线 softmax。
  • 编写 kernel 的门槛在降低：OpenAI 的 Triton 让人按“线程块”而不是按单个线程写 kernel（读进共享内存、算、写回），CS336 第 6 讲用它写了 GeLU、softmax 和矩阵乘；torch.compile 生成的融合 kernel 也是 Triton。
